## 2. Applying it on kind, for whoever wants to

Untested end to end — these are the steps the artifacts are written for, not a transcript of
a run that happened.

**Budget first.** The manifests request ~3.4 GB and limit to ~8 GB across nine workloads. The
reference laptop gives Docker 8.13 GB total, which is why this was never run here: a kind
node inside that VM, running the whole stack, has no headroom. A machine with 16 GB free is
the realistic floor.

```bash
# 1. A cluster.
kind create cluster --name vigil

# 2. The image. kind has no registry, so load it directly -- this is why every
#    workload sets imagePullPolicy: IfNotPresent.
docker build -t vigil:0.1.0 .
kind load docker-image vigil:0.1.0 --name vigil

# 3. Namespace, quota, limits and the Secret with generated passwords.
cd terraform
terraform init
terraform apply -var kubeconfig_context=kind-vigil
cd ..

# 4. The workloads. The Secret already exists, so 02-secret.template.yaml is not applied
#    and must not be -- it would overwrite real credentials with the string REPLACE_ME.
kubectl apply -k k8s/

# 5. Watch it come up. The stores must be ready before the consumers stop crash-looping;
#    there are no init containers gating that, so expect restarts on first apply.
kubectl -n vigil get pods -w
```

Optional pieces, deliberately outside the default apply set:

```bash
# Flink. Needs the image from flink/Dockerfile and ~2.5 GB on top of everything else.
docker build -t vigil/flink:1.20.1-py flink/
kind load docker-image vigil/flink:1.20.1-py --name vigil
kubectl apply -f k8s/30-flink.yaml

# The agent quality CronJob, and the synthetic load generator (scaled to 0 by default).
kubectl apply -f k8s/40-agent-quality-job.yaml
kubectl -n vigil scale deploy/loadgen --replicas=1

# The dashboard.
kubectl -n vigil port-forward svc/vigil-api 8000:8000
```

### Tearing down

kubectl delete -k k8s/

## 3. What Terraform owns, and why it is not the manifests

The Kubernetes provider can express every Deployment in HCL. Doing that would mean two
descriptions of one system, and they drift the first time someone edits only one. So the
split is (ADR-047):

- **`k8s/` describes the workloads.** It is the source of truth for what runs.
- **`terraform/` owns what sits around them**: namespace lifecycle, a `ResourceQuota` that
  stops a careless `kubectl scale` from eating the node, a `LimitRange` so a later manifest
  that forgets resources still gets defaults, and the Secret's *existence*.

Passwords are generated by `random_password`, not passed in as variables — that keeps them
out of a tfvars file and out of shell history. **It puts them in Terraform state, which is
therefore sensitive**: `terraform/.gitignore` excludes `*.tfstate` as its first line, and
that exclusion is the single most important line in this directory. They are deliberately
not outputs either, because an output invites `terraform output -raw`, which is a live
credential in a shell history. Read one from the cluster when you actually need it:

```bash
kubectl -n vigil get secret vigil-secrets -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 -d
```

**No cloud provider is configured.** An `aws_eks_cluster` or `google_container_cluster` block
would be the most impressive-looking file in this repository and the least honest: nothing in
it would ever have been applied, and neither free tier includes a managed control plane.

## 4. Deployment topology, and where it differs from compose

| Concern | Compose | Kubernetes |
|---|---|---|
| Kafka | one container, host listener on 19092 | StatefulSet, headless Service, in-cluster listener only |
| Stores | named volumes | `volumeClaimTemplates`, 45 GiB across the four |
| Config | `.env` | `vigil-config` ConfigMap + `vigil-secrets` Secret |
| Flink | compose profile | separate manifest, outside the default apply set |
| API | one process | Deployment, 2 replicas behind a Service |
| Consumers | run by hand | four single-replica Deployments |

Three properties carried across deliberately:

- **Single-broker Kafka, replication factor 1.** Raising `replicas` would give three brokers
  that still cannot replicate, because the replication factors are 1. The limitation is real
  (no leader election, no ISR shrink) and is gap G-4.
- **The lake sink is pinned to one replica with `strategy: Recreate`.** It manages its own
  partition assignment because its offsets live in the Iceberg snapshot (ADR-044); two
  replicas would both claim the same partitions and write the same rows.
- **Flink checkpoints are on `emptyDir`,** so they do not survive the pod. Enough to exercise
  exactly-once within a pod lifetime, which is what the chaos suite tested. Surviving a
  JobManager loss needs a shared PersistentVolume or object storage — the MinIO in this stack
  would do, and that is the upgrade rather than a rewrite.

## 5. Probes: where they exist and where they do not

The API, Kafka, Postgres, ClickHouse, MinIO and the Flink JobManager all have readiness and
liveness probes that check something real.

**The four consumers — detector, reconciler, warehouse-sink, lake-sink — have none, and that
is deliberate.** They serve no HTTP. A readiness probe gates Service endpoints and nothing
routes to a consumer, so its value would be read by nobody. For liveness, the available
options are all bad:

- `exec: ["true"]` or a `pgrep` on PID 1 passes whenever the container is up, which the
  kubelet already knows. Decoration.
- Probing Kafka reachability restarts the consumer when the *broker* is down, which is
  precisely when it should sit and retry rather than thrash.
- A heartbeat file touched by the poll loop and checked with `test -newermt` is the only one
  that detects a genuinely wedged consumer — and it needs the application to write that file.

So the liveness signal is the one Kubernetes gives for free: the process exits, the container
dies, the pod restarts. **The heartbeat file is the honest upgrade**, it is application work
in the four consumer loops, and it has not been done.

## 6. What is NOT validated

Static validation proves these files are well-formed, schema-valid and internally consistent.
It proves nothing about runtime. Specifically **unverified**:

- **That the stack comes up.** No pod has ever been scheduled from these manifests. Ordering,
  crash-loop behaviour on first apply, and whether the readiness probes have the right
  timings are all untested.
- **That the probes pass against the real containers.** The ClickHouse probe is `httpGet
  /ping`, changed from the compose `wget` form to avoid the IPv6 trap that broke the compose
  healthcheck. That reasoning is sound and has not been observed working.
- **Resource requests and limits.** Derived from the compose measurement (1.2 GB across four
  services) plus headroom. Whether the consumers fit their limits under real load is unknown;
  the scale harness has never been pointed at a cluster.
- **PersistentVolume behaviour.** No StorageClass was exercised. `volumeClaimTemplates` on a
  cluster with no default StorageClass leaves the pods Pending, and nothing here checks for
  one.
- **Terraform apply.** `validate` parses and type-checks; it does not contact a cluster. The
  provider has never authenticated, and `kubernetes_resource_quota_v1` has never been created.
- **Prometheus scraping anything.** The rules and config parse. No Prometheus has scraped the
  API, so no alert has ever fired or resolved, and the `for:` durations are unexercised.
- **The Grafana dashboard rendering.** The JSON parses and every expression is valid PromQL
  against metrics that exist. It has not been loaded into Grafana.
- **Consumer-group lag alerting.** Cannot work at all: no exporter publishes
  `kafka_consumergroup_lag`. The rule is present, labelled `requires-kafka-exporter`, and
  routed to the null receiver.
