# Architecture Decision Records (ADRs)
### Real-Time Anomaly Detection & Self-Remediating Agent Platform
**SDLC phase:** Design — companion to `ARCHITECTURE.md`

> One decision per record: context, decision, alternatives, consequences (including the cost
> accepted). Add a new ADR when a real tradeoff is made; never overwrite history — supersede.

---

## ADR-001 — Zero-shot time-series foundation model as the detection spine
**Status:** accepted
**Context:** The stream is unlabeled and live; a detector must work without training labels.
**Decision:** Use a zero-shot foundation-model detector (Chronos-/TimesFM-class) on windowed batches.
**Alternatives:** train-from-scratch deep model (needs labels; heavy); supervised detector (no labels available); classical only (chosen instead as the *baseline*, not the spine).
**Consequences:** no labels needed; fits the serving stack. Cost: heavier per-window inference (mitigated by batching + a small/quantized model) and foundation-model AD is contested — hence the honest benchmark (ADR-008 / NFR-8).

## ADR-002 — Condition detection on reconciliation signals (the core mechanism)
**Status:** accepted
**Context:** Detectors fire on pipeline artifacts because they see only values, not pipeline health.
**Decision:** Feed the reconciliation harness's per-window pipeline-health signal into the detector as a conditioning input; attribute anomalies overlapping a proven disturbance to the pipeline.
**Alternatives:** keep DQ/reconciliation and detection separate (the status quo — the problem); post-hoc alert suppression rules (brittle, no provenance).
**Consequences:** the novel contribution; provable false-positive reduction. Cost: the reconciliation harness becomes **load-bearing for detection**, so it must be genuinely solid (this is the intended depth).

## ADR-003 — Generalize conditioning to deploy/change markers via a pluggable interface
**Status:** accepted
**Context:** Deploys are a top real-world false-positive trigger, distinct from pipeline faults.
**Decision:** Model conditioning as a `ContextSignalSource` interface; pipeline-health and deploy-markers are two instances. New signals implement the same interface.
**Alternatives:** hard-code only the pipeline signal (less general); build a bespoke path per signal (rework).
**Consequences:** one mechanism, extensible; the v2 roadmap (maintenance windows, feature flags) plugs in without redesign. Cost: a small amount of upfront interface design.

## ADR-004 — VLM explanation on flagged windows only
**Status:** accepted
**Context:** Operators need *why* to dismiss/triage; running a VLM on every window is too costly.
**Decision:** Run the VLM only on windows already flagged (the VLM4TS screen-then-verify pattern), producing an explanation attached to the episode.
**Alternatives:** VLM on every window (blows latency/cost); no explanation (less actionable).
**Consequences:** explainability with no hot-path cost. Cost: explanation latency on the rare path (acceptable, NFR-2). **Cite VLM4TS — this pattern is prior art, not our invention.**

## ADR-005 — Apache Flink for stateful exactly-once processing
**Status:** accepted
**Context:** Need event-time, large keyed state, and exactly-once — the data-platform signal.
**Decision:** Flink (event-time, watermarks, RocksDB state, checkpointing, 2PC exactly-once).
**Alternatives:** Kafka Streams (weaker for large state / event-time); Spark Structured Streaming (micro-batch, higher latency).
**Consequences:** strong exactly-once + windowing; the skill target for the primary role. Cost: operational complexity and a steeper learning curve.

## ADR-006 — Storage split: Postgres (episodes) · ClickHouse (serving) · Iceberg (source of truth)
**Status:** accepted
**Context:** Different needs: app state, fast dashboard queries, and a durable reconciliation reference.
**Decision:** Postgres for detected episodes/app state; ClickHouse for OLAP serving; Iceberg as the durable lake and reconciliation source of truth. Raw readings never go to Postgres.
**Alternatives:** one store for everything (wrong performance/durability tradeoffs).
**Consequences:** each store fits its job; reconciliation has a durable reference. Cost: more moving parts to run.

## ADR-007 — Conditioning fails open when the health signal is unavailable
**Status:** accepted
**Context:** If conditioning suppressed flags whenever context was missing, a signal outage could hide real anomalies.
**Decision:** When a context signal is unavailable, fall back to *unconditioned* detection — raise flags normally; never silently suppress.
**Alternatives:** fail-closed (suppress on missing context) — unsafe; block detection until context returns — unavailable when most needed.
**Consequences:** missing context can never hide a real anomaly. Cost: during a health-signal outage, artifact-driven false positives are not suppressed (correct tradeoff — safety over noise).

## ADR-008 — Solve context-conditioned detection deeply; defer alert-correlation & drift to v2
**Status:** accepted
**Context:** Five validated pains exist; solving all shallowly reads junior and invites scrutiny failures.
**Decision:** v1 solves context-conditioned false-positive suppression (pipeline + deploy) deeply and proves it; alert-correlation/flooding and drift/staleness are documented v2 roadmap.
**Alternatives:** build all five (breadth-over-depth); ignore the others (looks naive).
**Consequences:** one proven mechanism + a credible roadmap. Cost: v1 does not de-duplicate alerts or self-adapt to drift (accepted; the conditioning interface makes both reachable later).

## ADR-009 - JSON on the wire, no schema registry
**Status:** accepted (Phase 1)
**Context:** Every stage between ingestion and detection needs one agreed record format. The obvious production answer is Avro or Protobuf behind a schema registry.
**Decision:** Compact JSON, with the encode/decode pair defined once in `vigil.readings` and covered by round-trip tests.
**Alternatives:** Avro + Confluent Schema Registry (another always-on service on a 15.6 GB laptop, plus a codegen step, for a five-field record); Protobuf (same codegen cost, far less debuggable on the console consumer); MessagePack (compact, but no better schema story than JSON).
**Consequences:** `kafka-console-consumer` output is readable, which matters constantly while debugging the correctness story, and there is no extra service to keep alive. Cost: no enforced schema, larger payloads. Mitigated by the single codec module -- a field can only change in one place -- and measured: at the 20k events/s target the format costs roughly 2 MB/s before lz4, which is nowhere near the bottleneck (the producer sustained 76,556 events/s).

## ADR-010 - The public TDengine solar-fleet MQTT feed as the live source
**Status:** accepted (Phase 1); supersedes the "live feed TBD" note in PROJECT_PLAN section 9
**Context:** The plan called for a free, public, always-on feed and left the choice open; development had been proceeding on the synthetic generator.
**Decision:** `mqtt.tdengine.com:1883`, anonymous, QoS 0. Topics `sites`, `inverters`, `strings`, `weather`, `grid`. Default working set is `inverters`; `strings` is the high-rate topic for scale tests; `#` is exploration only. Configured via `MQTT_HOST` / `MQTT_PORT` / `MQTT_TOPIC`.
**Alternatives:** a crypto-exchange trade WebSocket (high rate, but a price series has no notion of "expected", so there is no physically meaningful residual and no operational context to condition on -- it would have gutted the core contribution); public transit GTFS-RT (low rate, polling rather than streaming); staying synthetic-only (no claim that the pipeline works on genuinely unseen data).
**Consequences:** This feed has the one property the project needs and a price stream does not: it publishes *expected* alongside *actual* (`Expected_Power_MW` vs `AC_Power_MW`, `Deviation_%` per string), so detection runs on a residual with physical meaning rather than on an arbitrary threshold. It also carries real operational context -- curtailment, soiling, alarms, weather -- which is the material the conditioning layer consumes in Phase 3. Measured 2026-09-06: strings ~504 msg/s, inverters ~30 msg/s, sites/weather/grid ~3.6 msg/s each. Cost: no SLA, no history, and a rate far below the throughput target, so the synthetic generator is retained as the scale and correctness harness (ADR-014). Citizenship: one connection per process, exponential reconnect backoff to a 60 s ceiling, identifying client id, QoS 0 as published.

## ADR-011 - The edge guarantee is at-most-once, with gap detection but no backfill
**Status:** accepted (Phase 1); corrects FR-1 and PROJECT_PLAN section 5.5
**Context:** The design assumed a WebSocket edge with gap detection *and REST backfill*, giving at-least-once at the boundary. The chosen feed is MQTT QoS 0 and publishes no history API.
**Decision:** State the edge guarantee as **at-most-once** and build detection without backfill. `IngestGapWatch` learns each channel's own cadence from the median of recent inter-arrival times and reports silence beyond a multiple of it. The interior guarantee (exactly-once inside Kafka/Flink) is unaffected and is where the correctness claim lives.
**Alternatives:** QoS 1 (the public broker's session behaviour is not ours to depend on, and it still recovers nothing dropped before we connected); claiming at-least-once anyway (false); dropping the live feed to preserve the original claim (loses the unseen-data property for a guarantee that only ever covered the edge).
**Consequences:** An honest, narrower claim. Cadence must be learned per channel rather than fixed globally because the same feed carries 500 msg/s string telemetry and 3.6 msg/s site rollups -- one threshold would either miss real outages on the fast channels or cry wolf on the slow ones. Median rather than mean, so one scheduling hiccup does not move the estimate; a detected gap is excluded from the estimate, so one long stall cannot raise the threshold enough to hide every later stall. Cost: edge loss is detectable but not repairable on the live source. Mitigation: the synthetic source has perfect sequence integrity by construction, so every correctness and chaos test runs against a stream where loss is unambiguous.

## ADR-012 - Fan messages out per (entity, metric); detect on the expected-vs-actual residual
**Status:** accepted (Phase 1)
**Context:** One MQTT message describes one entity at one instant with a dozen fields. The detector consumes univariate channels. Something must decide the mapping, and which field is *the* signal.
**Decision:** One reading per (entity, metric), channel named like `SITE_001.ac_power_mw`, identical in shape to the synthetic fleet so nothing downstream knows which source it is reading. The primary detection metric is the expected-vs-actual residual, not raw output: `Expected_Power_MW - AC_Power_MW` for sites, the feed's own `Deviation_%` for strings, `PR_Local` for inverters (which publish no expected-power field), `Setpoint_MW - Active_Power_MW` for grid meters.
**Alternatives:** publish each message as one multivariate record (forces every detector to know the feed's field names; TSB-AD-M already covers the multivariate benchmark case); detect on raw `AC_Power_MW` (fires on every sunset, fleet-wide, forever).
**Consequences:** The **sunset quirk** is handled by the choice of signal rather than by a special case: generation collapses every evening on every channel at once, but the residual sits near zero at noon *and* near zero at midnight, so nightfall is not an excursion. Raw power is still published as its own channel, deliberately -- it is the control that shows what an unconditioned detector does at sunset, and that comparison is the measurement in `docs/EVALUATION.md`. Any ratio this bridge *derives* is withheld below a production floor rather than emitted as a number invented by dividing near-zero by near-zero; fields the feed itself provides are always passed through, because judging them meaningless is the detector's job, informed by the irradiance channel, not the bridge's. Cost: roughly 8x message amplification (a measured 45 s run turned 1,387 MQTT messages into 11,089 readings across 336 channels).

## ADR-013 - TSB-AD-M as the labelled benchmark; threshold-independent metrics, never point-adjusted F1
**Status:** accepted (Phase 1, consumed in Phase 5)
**Context:** The live feed is unlabelled by construction, so precision and recall cannot be computed on it. A labelled corpus is required for the honest benchmark in NFR-8 and PROJECT_PLAN section 10.
**Decision:** TSB-AD-M, the multivariate track: 200 labelled series, 2.4 GB extracted, fetched on demand by `scripts/fetch_tsb_ad.py` into a git-ignored `Datasets/` (archive sha256 `7de86ac27f30eeb48d833bb061055670e3f3de07defd995cf2bd5db10ccc9a0d`). Report point-wise AUC-PR, VUS-PR and VUS-ROC, plus precision/recall/F1 at a *matched alarm budget*. **Point-adjusted F1 is not reported at all.**
**Alternatives:** MetroPT-3 alone (a single asset with one failure mode -- too thin to generalise from); deriving labels from the solar feed's own `Status` and `Alarm_Messages` (those are another detector's opinion, so scoring against them measures agreement with an unknown algorithm, not correctness); reporting point-adjusted F1 because most papers do.
**Consequences:** Point-adjustment marks an entire ground-truth range as detected if the detector fires even once inside it, which lets a near-random scorer post a high F1. That specific inflation is the reliability problem TSB-AD was built to expose, so adopting the benchmark and then using the metric it exists to discredit would be self-defeating. Accuracy and ROC-AUC are excluded for the same family of reasons: anomalies are well under 1% of points, so both are dominated by the negative class. Cost: our numbers will look *worse* than papers that point-adjust, and are not directly comparable to them. That is the intended trade. Environment note: TSB-AD's own package targets Python 3.11; we consume only the labelled CSVs and compute the metrics ourselves, so the platform stays on 3.12 and no second interpreter is needed.

## ADR-014 - Keep the synthetic generator as the harness, with AR(1) noise
**Status:** accepted (Phase 1)
**Context:** With a live feed adopted, the synthetic generator could have been deleted.
**Decision:** Keep it behind the same `ReadingSource` interface. It is the only source that can be seeded, replayed exactly, driven at an exact rate or unpaced, and that carries ground-truth labels inline. Its noise is AR(1) with the innovation scaled by sqrt(1 - phi^2), not white.
**Alternatives:** delete it and test against the live feed (throughput capped near 250 readings/s, no reproducibility, no labels, and a chaos suite whose results depend on a third party's uptime); white noise (simpler to write).
**Consequences:** Throughput, chaos and exactly-once tests are reproducible and independent of anyone else's availability. The AR(1) choice is deliberate methodology: independent samples keep a rolling standard deviation well behaved, so almost any excursion is caught and the z-score baseline looks far stronger than it is. Real sensor noise is autocorrelated, which inflates the running sigma and is what actually makes cheap detectors miss things. Scaling the innovation holds the stationary variance fixed, so changing the persistence cannot silently change the signal-to-noise ratio the benchmark runs at. Cost: a harder synthetic signal makes our own baseline numbers look worse, which is the point.

## ADR-015 - Schedule the evaluation adversarially, so blanket suppression fails visibly
**Status:** accepted (Phase 1, consumed in Phase 3)
**Context:** The core claim is a measured false-positive reduction during deploys and pipeline disturbances. There is a trivial way to post a large number: suppress everything inside a context window. A naive evaluation cannot distinguish that from correctly attributing an artifact to its cause, which would make the headline result unfalsifiable and worthless under scrutiny.
**Decision:** Build the generator so the cheat fails. `loadgen.py --scenario` schedules four populations deliberately: (1) deploys that **do** perturb telemetry, whose artifacts are the legitimate suppression target; (2) deploys that perturb **nothing** (`--quiet-deploy-fraction`, default 0.35), so suppression triggered by the marker alone has nothing to hide behind; (3) real faults **outside** every deploy window, as the control; (4) real faults **inside** deploy windows including quiet ones (`--fault-in-window-fraction`, default 0.40), which must still be detected. Deploys touch a **subset** of channels, and an artifact is only ever placed on a channel the deploy actually touched, so a policy that ignores scope over-suppresses and is caught. Markers go to a dedicated context topic (`ops.context`) and are published as the run reaches them, never dumped up front -- a policy that could see the whole future would be solving an easier problem than the real one. The same design is applied to pipeline artifacts through the chaos suite in Phase 2.
**Alternatives:** inject artifacts only, and report the suppression rate (the unfalsifiable version); inject real faults only outside windows (leaves recall-under-a-window untested, which is exactly where blanket muting hides); label everything one way and rely on manual inspection (does not scale and is not reproducible).
**Consequences:** Every reported false-positive reduction comes with a recall number computed on faults that were deliberately placed where a cheating policy would lose them, so the pair of numbers is meaningful rather than decorative. The plan is seeded and written to disk (`--write-plan`) before scoring, so ground truth is fixed before any detector sees the data. Cost: a substantially more complex generator, and a scenario run needs a fixed `--duration` because the plan is scheduled up front. Poisson anomalies are disabled under a scenario, since unplanned excursions would appear as detections the ground truth cannot account for.

## ADR-016 - Report false-positive reduction and recall as a pair, never a single number
**Status:** accepted (Phase 1); revises NFR-8
**Context:** NFR-8 was written as "at least 50% of artifact-driven false positives suppressed". Optimising a suppression rate on its own rewards exactly the failure mode ADR-015 was built to expose: the metric is maximised by suppressing everything.
**Decision:** The success criterion is a **pair**, always reported together and always against the *unconditioned* baseline on the same data: **at least 40% false-positive reduction during simulated deploys and pipeline faults, with approximately zero recall loss on real faults**. Report the precision/recall trade-off, not one figure. Recall is broken out for faults inside context windows and outside them, because the inside population is the one a cheating policy loses. Scoring uses threshold-independent, time-aware measures (VUS-style) consistent with the TSB-AD choice in ADR-013; **no point-adjustment**. A run of consecutive alarms on the same channel counts **once**, since an operator is paged once per incident and counting each window separately would let a chatty detector inflate both the false-positive count and the apparent reduction. A read-only **shadow pass** runs first to establish the unconditioned baseline on the identical data, so the comparison is a true A/B rather than two runs over different streams.
**Alternatives:** keep the single 50% target (rewards over-suppression); report F1 alone (hides which side of the trade moved); point-adjusted metrics (already rejected in ADR-013 for the same family of reasons).
**Consequences:** The headline claim becomes defensible: a reviewer can ask "what did it cost you in recall" and the answer is already in the table. The target moves from 50% to 40% because it is now a genuinely harder, paired target rather than an unconstrained suppression rate -- lowering it while adding the constraint is the honest direction. Cost: every evaluation run must be executed twice, once shadow and once conditioned. All deltas are reported including regressions.

## ADR-017 - The latency budget binds the hot path, not the foundation model
**Status:** accepted (Phase 1); revises NFR-1
**Context:** NFR-1 set 250 ms p99 per window. Pinning that to a time-series foundation model on this laptop is not achievable honestly: a 200M-class model runs roughly 200-500 ms per batch on CPU and effectively wants a GPU, and this machine has 4 GB of VRAM. Writing a target that can only be met by fudging the measurement is worse than writing an accurate one.
**Decision:** The 250 ms p99 budget applies to the **hot path** -- the detector on the critical path that every window must clear before an episode can be raised. The cheap z-score baseline stays there, optionally joined by a distilled or tiny detector (Chronos-Bolt or Tiny Time-Mixers class) if it measures within budget. The foundation model runs **batched and off the critical path**, contributing a second opinion and the benchmark comparison rather than gating the stream. Actual per-detector latency is measured and recorded, and the model is chosen to fit the budget rather than the budget stretched to fit the model. Final latency and throughput targets are locked only after Phase 2 produces the baseline and the scaling curve.
**Alternatives:** keep one budget covering every detector (either unachievable, or achievable only by quietly excluding the model from the measurement); drop the foundation model (abandons a stated goal and the honest benchmark that goes with it); require a GPU (violates the laptop constraint in NFR-13).
**Consequences:** The stream keeps a hard, measured latency bound that does not depend on model choice, and the foundation model can be evaluated on quality without its cost being hidden. Degradation is explicit and already in the design: if the model path is down or slow, the hot path is unaffected. Cost: the model's verdict arrives later than the baseline's, so an episode can be raised on the baseline and enriched afterwards -- the episode record must therefore carry per-detector scores rather than a single fused one. Numbers stated as targets here are provisional until Phase 2 measures them.

## ADR-018 - Build the reconciliation harness before Flink
**Status:** accepted (Phase 2)
**Context:** Phase 2 contains both the Flink migration and the reconciliation harness. The obvious order is Flink first, since the harness is described as auditing it.
**Decision:** Build the harness first, against the existing Python consumer.
**Alternatives:** Flink first, then a harness to audit it (the natural reading of the plan); build them together (neither would be trustworthy while the other was in flux).
**Consequences:** Two payoffs. First, the harness is **load-bearing for the core contribution**, not merely for the correctness claim -- the per-window health signal it emits is what conditioning consumes in Phase 3 -- so building it first unblocks the thing the project exists to demonstrate. Second, it turns the Flink migration into a *checkable* change: the harness records what the semantics were before, and the same harness run against the Flink job afterwards says whether they survived. Migrating first and auditing afterwards would have left no baseline to compare against. Cost: the harness had to be written against an interface that was about to change, which is why the ledger is pure and knows nothing about Kafka.

## ADR-019 - Watermarks take the minimum across sources, with an idleness timeout
**Status:** accepted (Phase 2)
**Context:** The harness closes a window once the stream has moved past it. The first implementation used the highest event time seen anywhere in the stream.
**Decision:** The watermark is the **minimum** event time across all non-idle sources, where a source is a Kafka partition. Partitions are registered on assignment rather than on first delivery, and a registered-but-silent source blocks the watermark entirely. A source that has said nothing for a configurable interval stops holding it back.
**Alternatives:** maximum across the stream (what was tried); a fixed grace period generous enough to absorb the skew (fragile -- the right value depends on consumption order, which is not knowable in advance); per-partition windows that are never combined (loses the fleet-wide view the health signal exists to give).
**Consequences:** Measured, on a 7-minute replay of 252,000 readings: the maximum-based version stranded **74%** of readings as arriving after their window had closed, and emitted **187,631** health windows where 15 were correct, because each late reading re-opened and re-emitted a window that had already been published. Switching to the minimum fixed the direction but still stranded **51%**, because sources were discovered lazily -- a partition Kafka had not yet served was indistinguishable from one that did not exist, so the minimum was taken over a subset. Registering on assignment took it to **0%**. The idleness timeout is required because Kafka partitions go quiet routinely and one silent partition would otherwise stall every window forever; this is the same problem Flink solves the same way, and the Flink job uses `withIdleness` for exactly this reason. Cost: a window cannot close until the slowest partition reaches it, so a badly lagging partition delays the health signal -- which is the correct trade, since publishing a health record for a window we have not finished reading would be a false statement.

## ADR-020 - Lag grading is separable from loss grading
**Status:** accepted (Phase 2)
**Context:** The health signal grades a window's severity from missing readings, duplicates, reordering, and lag. Lag is measured against the wall clock. Replaying a topic recorded minutes ago therefore reports minutes of lag and graded every window of every replay `critical`.
**Decision:** Keep measuring lag always, but make **grading** on it switchable (`--ignore-lag`). Replays and benchmarks turn it off and say so; live runs leave it on. Loss and duplicate grading are never affected.
**Alternatives:** raise the lag thresholds for replays (arbitrary, and hides genuine lag in live runs that happen to use the same config); drop lag from the signal (it is the most useful early warning of a pipeline falling behind); measure lag against ingestion time rather than event time (measures nothing -- ingestion time is when we read it, so the answer is always near zero).
**Consequences:** A replay no longer marks everything disturbed, which matters because a conditioning policy fed that signal would suppress every anomaly in the run. The measurement stays in the record either way, so nothing is hidden -- only the severity judgement changes, and the run states which mode it used. Cost: one more flag whose meaning has to be understood to read a result correctly.

## ADR-021 - A chaos scenario must prove it disrupted something
**Status:** accepted (Phase 2)
**Context:** The first full chaos run reported four passes. Inspecting the logs showed that two of them -- the broker pause and the network partition -- produced no observable disruption at all: the producer never logged an error, and the recovery check reported the broker serving again in 0.0 s. The runs were green and meaningless.
**Decision:** Every scenario samples serviceability once a second throughout the fault hold and records how many samples found the system unserviceable. **A scenario with zero unhealthy samples fails**, with a note saying the fault did not disrupt anything. The network-partition check was also fixed: it had been testing only the client path, and Docker's published-port proxy keeps answering the TCP handshake after a container leaves the network, so the check reported healthy throughout a partition that had genuinely been applied.
**Alternatives:** trust that injecting implies disrupting (what produced the false greens); assert on producer error counts alone (a client can ride out a short outage entirely from its retry buffer, which is correct behaviour and would look like a no-op); lengthen every hold until something visibly breaks (slow, and tunes the test until it passes rather than measuring the system).
**Consequences:** A green chaos result now means something specific: the system was measurably unserviceable, and it still recovered to a state the identity invariant accepts. Cost: some faults are genuinely hard to make bite on a single-node laptop broker, and those will now report failure rather than a comfortable pass. That is the intended direction -- `docs/CHAOS.md` reports what actually happened, including the modes that could not be made to disrupt this deployment.

## ADR-022 - Run Flink as containers with PyFlink, not as a host process or a Java job
**Status:** accepted (Phase 2)
**Context:** ADR-005 chose Flink for event-time processing, large keyed state and exactly-once via two-phase commit. It has to actually run on this machine.
**Decision:** A JobManager and a TaskManager as compose services behind a `flink` profile, built from `flink:1.20.1-scala_2.12-java17` with Python and PyFlink added. The job is `flink/scoring_job.py`, submitted to the cluster.
**Alternatives:** PyFlink in the host virtualenv (no wheel is published for Windows on Python 3.12, so it would mean a source build against a toolchain this machine does not have); a Java job (Java 17 is present, but it would mean a Maven build and a second implementation of the detector, so the migration could no longer be checked by comparing identical computations); Flink SQL only (does not exercise keyed state or a custom process function, which are the parts worth demonstrating).
**Consequences:** This is the deployment `ARCHITECTURE.md` section 9 already described, so it is the intended shape rather than a workaround. The job deliberately mirrors `vigil.detectors.zscore` computation for computation -- same Welford update, same decay, same score -- because the point of the migration is to show the semantics survived it, and that can only be shown if the two are the same calculation. Behind a profile because JobManager plus TaskManager want about 2.5 GB and the Docker VM has 8.1 GB with Kafka and Postgres already in it, so it is brought up deliberately rather than always running. Cost: an image build, a second Python runtime to keep in step with the first, and a job that cannot import the `vigil` package directly.

## ADR-023 - Drop VUS-PR rather than ship a version that punishes precision
**Status:** accepted (Phase 3); revises the metric list in ADR-013
**Context:** ADR-013 committed to reporting VUS-PR and VUS-ROC alongside point-wise AUC-PR, on the reasoning that a windowed detector localises an anomaly to within a window and a metric demanding exact point alignment measures window size rather than detection quality. That reasoning still holds. The implementation did not.
**Decision:** Remove it. The tolerant measure was built by dilating the label set and averaging AUC-PR over tolerances 0..30 -- the obvious shortcut -- and it was **measured against a case with a known answer**: a detector firing exactly on the labelled points and nowhere else, which had found the event perfectly. It scored **0.48**. Dilating labels makes the buffer count as positive, so a precise detector is penalised for not padding its answers, and a detector that smeared its output would have scored higher. A faithful VUS weights the buffer on both the true-positive and false-positive sides; ours did not, and calling it VUS-PR would have been a claim we could not defend.
**Alternatives:** dilate the *scores* instead of the labels by max-pooling (moves the same distortion to the precision denominator -- a perfect detector still loses); implement the decayed-buffer weighting properly (correct, but subtle enough that a half-right version is a real risk, and the value did not justify the care required here); keep the broken version because the number looked plausible (the failure mode this project exists to avoid); pull in a library (the obvious one defaults to point-adjusted scoring, which ADR-013 rules out).
**Consequences:** What replaces it does the same job with numbers that can be explained exactly: **detection latency** -- how many points into an event the detector first fires, reported as a distribution with missed events counted separately rather than averaged in -- plus **event-level detection rate** reported always and only next to point recall, so the gap between them is visible. That gap is the informative part: a high event rate with low point recall means the detector is clipping event edges rather than missing events. Latency expresses the tolerance question as a number with a unit instead of an integral over an arbitrary range. Cost: our results cannot be lined up against papers that report VUS-PR. They could not have been anyway -- see the point-adjustment refusal in ADR-013 -- and an incomparable honest number beats a comparable wrong one.

**Postscript, because it is the point of the ADR.** The bug was caught by a test asserting that a perfect detector scores 1.0. Without that test the metric would have shipped, every detector comparison in `docs/EVALUATION.md` would have been quietly skewed toward whichever detector smeared its output most, and the number would have looked entirely reasonable.

## ADR-024 - Corroboration across scope as the discriminator, and why it had to be synchrony
**Status:** accepted (Phase 3), revised once by measurement
**Context:** `ARCHITECTURE.md` section 4 specified the v1 conditioning policy as "if a pipeline disturbance or active deploy overlaps window T, mark the flag attributed". That rule is blanket suppression: a real fault during a deploy is still a real fault, and the adversarial generator (ADR-015) exists specifically to catch a policy that behaves this way.
**Decision:** Attribute an anomaly to a context event only when three things hold: the event's **scope** includes the channel; the excursion is **corroborated** by the channel's in-scope siblings moving **within a few seconds of it**; and, for pipeline events, the health record shows a **mechanism** -- actual loss, duplication or reordering -- that could have distorted a value. A pipeline window graded only on lag explains nothing, because lag delays a reading rather than changing it.
**Alternatives:** overlap alone (the specified rule -- measured, and it destroys recall); magnitude or shape matching between the artifact and the excursion (needs a model of what each deploy does to each channel, which does not exist); suppressing during a window but re-raising afterwards (delays every real fault by the length of a deploy, which is exactly when delay is most costly).
**Consequences and the correction.** The corroboration argument is physical: a deploy that perturbs telemetry perturbs the channels it touched -- a collector restart blips the whole batch -- while a real fault is a property of one device, since a bearing does not fail because a collector was redeployed. The first implementation asked whether in-scope siblings were flagged **anywhere in the same 30-second window**, and that version was measured and **failed**: `isolated` was returned zero times out of 79 episodes, and every real fault inside a quiet deploy window was suppressed. With 56 artifacts and 30 faults across 12 channels and overlapping deploys covering nearly the whole run, two in-scope channels are flagged in almost any window by coincidence. The fix is **synchrony**: siblings must have started within a tight tolerance (default 5 s), because a deploy artifact is simultaneous across its scope and two independent faults in the same window are not. Both measurements are published in `docs/EVALUATION.md` section 3.4; reporting only the second would be tuning until it passes. Cost: the tolerance is a parameter, and a genuinely slow-rolling deploy that perturbs its channels minutes apart will not be attributed.

## ADR-025 - A scope of one explains nothing
**Status:** accepted (Phase 3)
**Context:** A context event scoped to a single channel has no siblings, so the corroboration test has no evidence in either direction.
**Decision:** Raise the episode. "Cannot tell" is treated as "raise", by the same reasoning as fail-open.
**Alternatives:** attribute (there is a deploy, it touched this channel, and nothing contradicts it); ask for more evidence (there is none to ask for).
**Consequences:** Consistent with ADR-007: absence of evidence never suppresses. It also closes a trivial attack on the mechanism -- declaring every deploy single-channel would otherwise suppress everything. Cost: a genuinely narrow deploy that really did cause an excursion will page someone.

## ADR-026 - The agent emits typed actions, never commands
**Status:** accepted (Phase 4)
**Context:** NFR-11 requires that 100% of agent actions pass a deterministic gate. Whether that is achievable at all depends on what an action is allowed to be.
**Decision:** A closed set of typed verbs with typed parameters. No shell, no free-form API calls, no code. An unknown verb is rejected at parse time rather than forwarded. Nothing irreversible is in the set at all.
**Alternatives:** shell commands behind an allow-list of binaries (to decide whether `sh -c "..."` is safe you must understand shell, at which point the gate is an interpreter with an attack surface); MCP tools with free-form arguments (better, but the arguments are still unconstrained); a model that self-limits (a planner that could be trusted to self-limit would not need a gate).
**Consequences:** The gate becomes a lookup and a handful of range checks, which is why it can be tested exhaustively rather than sampled. Adding a verb requires an entry, a risk classification and a sandbox implementation, and that friction is the feature. Cost: the agent cannot do anything nobody anticipated -- which is the intended trade, and the reason `escalate_to_human` is always available and never counts against a budget.

## ADR-027 - The gate never reads the agent's rationale
**Status:** accepted (Phase 4)
**Context:** A proposed action arrives with the reasoning behind it. The obvious design lets the gate weigh that reasoning.
**Decision:** It does not. The gate reads the action and the episode. The rationale is recorded in the trace for a human and is not an input to the decision.
**Alternatives:** weigh the rationale (a channel through which a model can persuade, and a component whose job is to be unpersuadable should not have one); weigh a confidence score (same objection, with a number instead of prose); have a second model review the first (two models that can be talked around instead of one).
**Consequences:** A test proves a rationale claiming on-call approval and incident-time policy exemption receives the identical verdict to no rationale at all. Risk is a fixed lookup per verb rather than derived from parameters, for the same reason: a gate that re-derived risk could be argued into a different answer by a well-chosen parameter. Cost: the gate cannot be more permissive in a genuine emergency, which is what `escalate_to_human` is for.

## ADR-028 - An attributed episode gets no remediation
**Status:** accepted (Phase 4)
**Context:** The agent acts on episodes. Conditioning marks some of them as explained by an operational event.
**Decision:** Any state-changing action on an episode that is not `real` is refused by the gate. Read-only investigation is still allowed.
**Alternatives:** act anyway (attributing an artifact to its cause and then silencing the channel would undo the attribution entirely); make it a planner rule (a planner is replaceable and this is a safety property, so it belongs in the gate).
**Consequences:** The core contribution and the agent are interlocked: conditioning does not merely change what an operator sees, it changes what the system is permitted to do. Investigation stays available because investigating is not remediating, and an operator reviewing the system's reasoning needs the evidence reachable. Cost: a genuine fault mis-attributed by conditioning is also protected from remediation -- which is why the recall half of NFR-8 matters as much as the false-positive half.

## ADR-029 - BM25 for runbook retrieval, not embeddings
**Status:** accepted (Phase 4)
**Context:** The agent's plan must be grounded in operational documents rather than improvised.
**Decision:** Lexical BM25 over passages split at runbook headings, with each passage naming the actions it licenses.
**Alternatives:** a dense retriever (weights to load, a service to run, and per-query latency, for a corpus of tens of documents); a hybrid (the complexity of both for a corpus this size); no retrieval, rules only (a plan with no citation is a plan whose wrongness is untraceable).
**Consequences:** Queries here are dominated by exact operational vocabulary -- channel names, metric names, fault kinds -- which lexical matching handles well, and tokenisation keeps underscores so `bearing_temp_c` stays one term rather than becoming three. Splitting at headings rather than a fixed chunk size respects the fact that an operational document is already organised by symptom. The licence line is what makes retrieval *bound* the plan rather than merely inform it: the planner intersects its proposals with what the retrieved passages permit, so a wrong action is traceable to a document. Cost: a genuine paraphrase will be missed, and this is a real limitation rather than a theoretical one. When retrieval finds nothing the plan is to escalate, which is the correct answer to "the runbooks do not cover this".

## ADR-030 - An agent that can propose nothing escalates instead of falling silent
**Status:** accepted (Phase 4, found while building the Phase 5 training set)
**Context:** `RunbookPlanner` intersects its proposals with what the retrieved passages license (ADR-029). When retrieval returns nothing it escalates -- but when retrieval *matched* and licensed nothing applicable to the symptom, it returned an empty list. `RemediationAgent.handle` then iterated over nothing: no proposal, no gate decision, no trace. An episode handled that way is indistinguishable in the record from an episode nobody looked at. Measured on a deliberately thin runbook index, 58 of 200 generated episodes took that path.
**Decision:** Abstention is an action, not an absence. The planner returns a single `escalate_to_human` when nothing it retrieved licenses an applicable action, and `RemediationAgent` applies the same fallback to *any* planner that returns an empty plan.
**Alternatives:** leave it to each planner (the seam accepts a model-backed planner, and a model returning `[]` is a likely failure mode -- the agent should not depend on the planner abstaining correctly); record a no-op step instead of escalating (keeps the trace but leaves nobody responsible for an episode the runbooks do not cover); propose an unlicensed read-only action such as `describe_channel` (invents grounding that no passage gave).
**Consequences:** Every handled episode now produces at least one gated decision, so "handled and nothing was proposed" cannot be silent. Escalation is not licensed by any passage, which is deliberate: escalation is the absence of a remediation rather than one, and the gate already permits it unconditionally. Cost: a thin runbook set produces more escalations, which is the honest signal that runbook coverage -- not the agent -- is what needs work.

## ADR-031 - The training set's abstention population is constructed, and says so
**Status:** accepted (Phase 5)
**Context:** The tool-calling training set is meant to carry four populations, one of which teaches the model to abstain when the runbooks do not cover a case. Measured on 1,200 generated episodes, that population was **empty**: every symptom the diagnoser can name has a runbook, and the diagnosis query shares vocabulary with those passages, so BM25 always returned something (in-domain top score: median 11.6, minimum 6.8; genuinely out-of-domain queries score 0 and return nothing).
**Decision:** Mark a fraction of generated episodes (default 10%) as belonging to an asset class with no runbook, and retrieve those against an empty index. The prompt the model sees is the real prompt for that condition -- "(none matched)" -- and the target is the single escalation that condition calls for. The construction is named in the module docstring rather than left to look emergent.
**Alternatives:** drop the population and the claim (loses the behaviour most likely to matter in deployment, where runbooks always lag the fleet); add out-of-domain vocabulary to the episode generator so retrieval misses naturally (the query template itself carries the shared terms, so this does not work without making the episodes unrealistic); lower the retrieval floor so weak matches are discarded (changes live agent behaviour to fix a dataset gap, and picks a threshold with no evidence behind it).
**Consequences:** The set contains all four populations (measured at 1,200 episodes: distilled 591, generalisation 376, safety 136, abstention 97) and a test fails if any is empty. The honest limitation: this teaches abstention on the *empty-retrieval* condition only. The other abstention condition -- passages retrieved that license nothing applicable -- is now handled deterministically by the planner (ADR-030), so the model is never trained on it, and the eval must not claim it was.

## ADR-032 - The CI quality gate measures structure, not judgement, and says which
**Status:** accepted (Phase 5)
**Context:** Phase 5 asks for a quality gate that fails the build on a regression, and names Ragas, DeepEval and TruLens. All three judge with an LLM, and there is no API key in this environment (BLOCKERS C-2). The options were to ship something judge-shaped that cannot run, to wait, or to measure what is measurable without a judge.
**Decision:** `agent_quality.py` measures the agent's **structural** properties over a fixed 400-episode set -- grounding rate, gate-approval rate, sandbox containment, safety-channel compliance, abstention correctness, silent runs, ungated executions -- and fails on either a broken absolute floor or a rate drifting below a committed baseline. It prints, every run, that judged metrics are not measured here and why.
**Alternatives:** wire DeepEval and let CI skip it without a key (a gate that never runs is a gate in name, and the skip would be invisible in a green build); a mocked judge (measures the mock); wait for a key (blocks the phase on someone else, and structural failures are the ones a refactor actually causes).
**Consequences:** The properties the design claims outright are now enforced on every commit rather than asserted once. Measured over 400 episodes: 1,267 actions, 100% grounded, 100% gate-approved, 100% sandboxed, 97.1% citing a runbook. The baseline is not decoration -- a planner that escalates everything breaks no floor, because escalation is grounded, approved and sandboxed by definition, and only a comparison against previous behaviour notices that the agent stopped doing anything. There is a test for exactly that. Cost: faithfulness, answer relevance and diagnosis correctness are unmeasured, and the gate must never be described as covering them.

## ADR-033 - A chaos scenario must prove recovery happened, not just that health returned
**Status:** accepted (Phase 2, extends ADR-021)
**Context:** ADR-021 made a scenario prove it disrupted something. The Flink checkpoint-recovery run showed the mirror-image hole: it reported 0.1 s recovery and PASS for a job that had not redeployed. Flink detects a dead TaskManager by heartbeat timeout, and until that fires the JobManager reports the job RUNNING with every task running -- so a health check asking "is the job up" is satisfied by a job whose tasks are already dead. The real redeploy happened about 50 seconds later.
**Decision:** Recovery must be evidenced by a **change of state that only recovery produces**. For Flink that is the vertex deployment timestamps having moved since injection; the scenario records them at inject time and requires them to advance. Injecting onto a cluster with no running job is refused outright.
**Alternatives:** lower `heartbeat.timeout` so failure is detected faster (tunes the system under test to make the test convenient, and trades detection latency against false failure detection under load -- a real production decision, not a testing one); wait a fixed grace period before measuring (picks a number with nothing behind it, and would still pass a job that never restarted); compare checkpoint restore counts (works, but is Flink-specific in a way the vertex timestamps are not, and the restore count also increments on restarts that acquire no slots).
**Consequences:** The scenario now measures 14.9 s of real recovery instead of 0.1 s of nothing, and the hold has to exceed the heartbeat timeout for the failure to be detected at all -- which is documented in `docs/CHAOS.md` section 2.1 rather than left as a magic number. The general principle costs something: every future fault needs a recovery signal specific to it, which is more work than reusing a liveness probe, and that work is the point.

## ADR-034 - The explainer renders a picture, and writes nothing when it has no model
**Status:** accepted (Phase 4, implementing ADR-004 and B-1)
**Context:** ADR-004 puts explanation on flagged windows only; B-1 chose a hosted endpoint because 4 GB of VRAM will not hold a useful VLM. What remained was how to represent a window to the model, and what an episode should carry when no model answered. Note that `docs/BLOCKERS.md` claimed this component was built for a day before it was -- the correction is part of this decision's record.
**Decision:** Render the flagged window and its preceding history as a PNG with the window shaded, and send it to an OpenAI-compatible endpoint with the episode's numbers as text. Every failure -- no key, unreachable endpoint, timeout, non-200, empty completion, unrenderable window -- returns an `Explanation` that is *unavailable with a reason*, and the episode's `explanation` column is left **empty** rather than filled with that reason.
**Alternatives:** send the raw samples as text (asks a language model to do signal processing in tokens, and abandons the flagged-window VLM pattern this follows -- VLM4TS, `docs/PROJECT_PLAN.md` section 15.2, whose premise is that a plot is the representation these models were trained on); write the failure reason into the explanation column (puts an infrastructure note where an operator expects a description of the anomaly, and a column full of "no API key" is worse than an empty one); run a small local VLM (does not fit, per C-1); explain every window rather than flagged ones (a per-window API call, which is the cost ADR-004 exists to avoid).
**Consequences:** Explanations cost one render and one API call per *episode*, not per window -- rare by construction. The rendering and the request are both tested, the success path against a local fake endpoint, so the contract is verified without a key; what cannot be verified without one is NFR-2's latency and whether the output is any good. The explainer runs on a bounded queue off the detection path, so a slow endpoint costs latency in the explanation and nothing in detection, and a full queue drops and counts rather than growing. An attributed episode is deliberately not explained: it has already been explained by the context event it was attributed to.

## ADR-035 - The episode carries the time it began, not the boundary that noticed it
**Status:** accepted (Phase 3, fixes the defect behind B-4)
**Context:** An episode was timestamped with the start of the window that flagged it. Windows slide by 10 s, so the only start differences two episodes could express were 0, 10, 20 ... seconds. The conditioning policy's synchrony test asks whether in-scope siblings moved within 5 s, and against a 10 s grid that question has exactly one satisfiable answer: identical bucket. Both published conditioning measurements (v1 at a 30 s window, v2 at 5 s) therefore asked a bucket-coincidence question rather than the synchrony question they claimed. Ground truth for the same run puts consecutive in-scope artifact onsets a median 1.8 s apart -- entirely below the grid.
**Decision:** A detector reports `onset_ms`, the event time of the reading that drove the score: the first sample departing from the reference by 3 sigma, or the most extreme sample when none crosses that line. An episode takes its onset from the window that *opened* it, and `Episode.began_ms` falls back to the window start when no onset exists. Conditioning compares `began_ms`.
**Alternatives:** the timestamp of the maximum-deviation sample rather than the first crossing (for a sustained step the argmax is noise-driven and lands anywhere in the departed region, which is worse for synchrony than the onset); a per-episode minimum over all its windows (later windows of a sustained excursion are departed from their first sample, so their honest onsets sit on window boundaries and would drag the value back onto the grid); shrinking the window slide to make the boundary finer (changes the detector's statistics to fix a bookkeeping problem, and 1 s windows have no statistics); accepting the quantised comparison and dropping the synchrony criterion (abandons the hypothesis without ever testing it).
**Consequences:** Measured over a 420-second synthetic scenario, all 35 episodes now carry onsets strictly off the 10 s grid, spread from 0 to 27 s inside their window -- so a sub-window tolerance means something for the first time. The onset is persisted, nullable, so "no onset" stays distinguishable from "the boundary"; the foundation-model path reports none and degrades to the old behaviour rather than losing the comparison. Cost: `3.0` sigma is a constant, and it decides which of two nearby samples is named when several depart at once. It is the conventional outlier boundary rather than a tuned value, and the fallback branch covers the case where nothing crosses it. Honest limitation: when an excursion began before the first flagged window, the onset is that window's start and the true onset is unrecoverable -- the detector cannot see earlier than the window that noticed.

## ADR-036 - The fine-tune's task is reshaped rather than dropped, with the teacher named as the ceiling
**Status:** accepted (Phase 5, answers B-3 option 2)
**Context:** B-3 measured the first training set and found five distinct targets, each a deterministic function of a symptom `Diagnoser` computes before the prompt is rendered and then includes in it. A model trained on that learns a five-way classification whose answer is one of its own inputs. The options were to drop the fine-tune, to reshape the task, or to ship it as distillation and say so.
**Decision:** Reshape. The prompt withholds the symptom, the diagnosis summary and the licence list, and carries the detector's per-window evidence instead. The cases are five shapes outside what `Diagnoser` can name -- and because it has no fall-through, they are misclassified rather than abstained on, so the rules are actively wrong rather than merely quiet. Retrieval returns the matching entry plus two distractors, and the held-out split states every licence in prose, so the entry must be identified from the evidence before its licence can be read. Targets come from a teacher policy written in `vigil.tuning.hard.TEACHER`, one entry per shape with its operational justification.
**Alternatives:** drop the fine-tune and publish the measurement (B-3 option 1: honest, cheap, and gives up on the one part of the plan that involves training anything); train on the original set and describe it as distillation (B-3 option 3: the write-up would have to say the model cannot exceed the rules, which is a strange thing to spend a GPU proving); teach `Diagnoser` the five new shapes and keep the easy set (removes the headroom entirely -- the rules would then be right and the fine-tune pointless again, which is why a test asserts the baseline stays bad); generate targets with a larger model instead of a written policy (moves the ceiling to an unexamined third party and makes the justification unreviewable).
**Consequences:** The gap is measured, not assumed: on 300 held-out cases the deployed planner scores **0% exact-match as deployed** and **20% given licence sets it could not have parsed**, with a forbidden action on 61% of the generous run. Both are reported. The ceiling is the teacher, so the model can reach that policy and not exceed it -- what is being measured is how much of the rules-to-teacher gap a fine-tune closes, which is a real question with a real answer. The gate and the deterministic planner are unchanged, so the baseline stays honest and no proposal escapes the same safety checks. Costs: the teacher is five hand-written policies that can be argued with, which is deliberate but is still a human judgement standing in for ground truth; and the training has **not been run** here, so nothing in the repository comes from an adapter.

## ADR-037 - A conditioning verdict waits behind an event-time barrier, and the evidence is recorded when it exists
**Status:** accepted (Phase 3, addresses G-7, the root cause behind B-4)
**Context:** Four measurements of the conditioning policy (v1-v3 and the low-density row) all found the corroboration test returning `isolated` almost never -- 0 of 79, 0 of 78, 0 of 76. The diagnosis was not that channels move together, but that the verdict was being taken before the evidence existed. Two mechanisms caused it. The corroboration index was filled when an episode **closed**, so a two-minute excursion contributed nothing about its first second until two minutes later. And the verdict fired the instant an episode closed, against whichever siblings happened to have finished first, which makes the answer a function of episode length and close order rather than of the world. No statistical discriminator can separate populations from data that has not arrived.
**Decision:** Two changes, both in event time. (1) `EpisodeBuilder` announces an episode when it **opens** -- on its first flagged window -- and conditioning records the departure then. (2) A closed episode is held in a `CorroborationBarrier` until the **fleet watermark**, the minimum across channels, has passed its onset by a configurable buffer (default 30 s). The minimum, not the maximum, because a question about several channels is only answerable once the slowest has passed the span it asks about; ADR-019's idleness rule keeps one silent device from freezing every verdict. The policy now also counts, per scoped decision, how many in-scope siblings were synchronous and how many were present at all, so "moved alone" and "nobody had arrived" stay distinguishable in every future run.
**Alternatives:** a processing-time delay (says "wait 30 seconds of wall clock", which on a replay of an hour of history waits for nothing and on a backlogged stream waits for the wrong span -- the delay has to be a statement about the data); a batch pass over completed windows after the run (removes the asymmetry and also removes the streaming claim, since the policy would no longer be one a live pipeline could run); recording every flagged window in the index rather than only the opening one (a sustained excursion would then corroborate itself at every window, which is the v1 coincidence problem rebuilt); widening the synchrony tolerance until siblings fall inside it (tunes a threshold to compensate for missing data, and v1 already measured where that ends).
**Consequences:** The barrier's cost is detection latency and it is measured rather than assumed -- `hold_report()` prints how many verdicts were actually delayed past their episode's close and by how much in event time, which is not the buffer, because an episode that outlasts its own buffer waits for nothing. `--verdict-buffer-ms 0` reproduces the racing behaviour exactly, so v1-v3 remain reproducible rather than becoming unrepeatable history. The fleet watermark is a stronger requirement than the per-channel one the windowing uses, and deliberately so: windowing is a per-channel question and conditioning is not. Cost accepted: an episode is now raised at least one buffer of event time after it began, on top of the window geometry NFR-3 already runs into (B-5), and a bounded replay ends with the last episodes decided on flush against whatever evidence exists -- counted separately so the two populations are never mixed.

## ADR-038 - Attribution requires the shape of a blast radius, not only the timing of one
**Status:** accepted (Phase 3, supersedes the discriminator half of ADR-024)
**Context:** With the evidence-arrival defect fixed (ADR-037) the corroboration test finally fires -- 21 attributions where v3 managed 7 -- and firing reveals that timing is the wrong criterion rather than a starved one. False-positive reduction rose to 27.8% and recall loss rose with it, from 6.7% to 16.7% (`docs/EVALUATION.md` section 3.8). The reason is physical: a pump seizing moves its own vibration, bearing temperature and flow within seconds of each other, and if that pump sits inside a deploy's scope then synchrony, scope and fraction all say "deploy". A timing-only policy cannot separate a machine failing from a rollout arriving, because on the axis it measures they are the same event.
**Decision:** Attribute only when the perturbation has the *shape* of the rollout rather than of a failure domain. A `FleetTopology` inventory places every channel on a node, a rack and a deploy ring; the policy takes the footprint of the channels that actually moved and refuses attribution when (a) they are confined to one machine, (b) they are confined to one cabinet while the deploy reached several, or (c) the deploy's own declared radius is one machine, in which case a rollout and a fault leave the same footprint and no evidence could separate them. Rings are assigned round-robin over nodes, which is not an implementation detail but the load-bearing assumption: deploy rings are laid out across physical failure domains precisely so that a cabinet losing power and a ring going bad do not look alike, and a ring assigned in contiguous blocks would be indistinguishable from a rack.
**Alternatives:** a concentration *fraction* with a threshold (invites tuning until the number passes, and "confined to one failure domain" is a fact about the graph rather than a matter of degree); learning the inter-channel correlation structure from data, as MSCRED does (arXiv 1811.08055) -- it works, and it makes the reason for a suppression a matter of inspecting a correlation matrix rather than reading a sentence, which is the wrong trade for a policy that decides whether to page a human; magnitude and direction agreement across scope (the other candidate named at the end of B-4: it is still a statistical test over the same channels, so a machine fault that moves three of its metrics the same way still passes); putting the ring on the deploy marker instead of deriving the footprint from scope plus inventory (the marker already names its channels, so the ring adds nothing the scope does not carry, while adding a wire field that can disagree with the inventory).
**Consequences:** The discriminator is threshold-free and its reasons are readable -- "every channel that moved sits on pump-02, while deploy-0007 reached three machines" is something an operator can check against a rack diagram. The topology test can only ever *refuse*: it removes attributions and never adds them, so it cannot become a second route to suppression. Without an inventory it raises no objection at all, which keeps a missing CMDB from silently turning conditioning off; the same holds for a channel the inventory does not list. Costs accepted, and they are real. **A rollout to one machine is now unattributable by construction** (ADR-025's reasoning applied to shape), and roughly a fifth of the generated deploys are exactly that, so false-positive reduction is given up on them deliberately. The rack test only runs where the fleet has more than one cabinet, so at 12 channels -- three machines in one rack -- the hierarchy collapses to the node level and the run says so rather than claiming a level it did not exercise. And the honest limitation: **the generator that places the faults and the policy that reads the topology share a model of the world.** The discriminator is being scored on data built to have the structure it looks for. What that measures is whether the mechanism works given the premise, not whether the premise holds in a real fleet; the premise -- that rings cut across failure domains and that a machine's metrics fail together -- is an operational claim about deploy practice, and it is stated here so it can be argued with rather than buried in a number. It is recorded as gap G-15.


## ADR-039 — Completion-only masking via collator, fp16 on V100, and a memory-safe resumable eval
**Status:** accepted
**Context:** B-3's GPU run landed on a Northeastern Explorer V100-SXM2-32GB with the pinned stack (transformers 4.46.3, trl 0.13.0, peft 0.13.2). Three things in the training/eval path did not survive contact with that hardware and library set: (1) the intended `completion_only_loss=True` flag does not exist in trl 0.13.0's `SFTConfig`; (2) the config requested bf16, which Volta has no native support for; (3) the in-training eval pass and the standalone eval both OOM'd or ran blind against 300 sequential generations.
**Decision:** (1) Get completion-only masking the way trl 0.13.0 supports it — feed a single `text` field (prompt+completion) and mask the prompt with `DataCollatorForCompletionOnlyLM` keyed to the Qwen assistant header `<|im_start|>assistant\n`; verified on the tokenizer alone (31 prompt tokens masked, 11 answer tokens trained, loss computed only on the answer). (2) Train and serve in **fp16**, not bf16, and set `bnb_4bit_compute_dtype=float16` to match — the adapter is served under the same quantisation it was trained against. (3) Disable in-training eval (`eval_strategy="no"`), run scoring as its own process, and make it resumable — each case is appended to `artifacts/planner-eval-progress.jsonl` as it completes, so a killed run resumes instead of restarting.
**Alternatives:** upgrade trl to ≥0.19 for the `completion_only_loss` flag (rejected: a multi-package bump — trl + transformers + peft — on a flaky NFS `/home`, high breakage risk for a flag whose behaviour the collator already gives); rent a bf16-capable GPU per the original B-3 spec (rejected: the V100 was what was available, and fp16 proved sufficient); run eval in one long window (rejected: a 40-minute interactive cap killed the run at case 177/300 with nothing saved — the reason resume exists).
**Consequences:** B-3 trained and scored on available hardware with no dependency changes: 1 epoch, 75 steps, 34.6 min, final train_loss 0.034, no NaN in any of the 75 logged steps — fp16 was stable on this task, contrary to the BLOCKERS.md B-3 caution, which is left standing as a correct *prior* warning. Cost accepted: (a) the collator path required reshaping the dataset to a single `text` field rather than the trl-native prompt/completion columns; (b) fp16 is a documented deviation from the bf16 spec, so the numbers describe an fp16-trained NF4 adapter, not the bf16 one the spec assumed; (c) eval p50 latency is ~15.8 s/plan — an artifact of 4-bit sequential generation on a V100, not the deployed path, and reported as such in `docs/results/planner-eval.md`.
## ADR-040 - Out-of-set symptoms and prose licences are what made the fine-tune winnable, and the margin is now measured
**Status:** accepted (Phase 5, closes B-3)
**Context:** ADR-036 reshaped the planner fine-tune's task on an argument rather than a measurement. The claim was that three properties -- symptoms outside the five `Diagnoser` can name (so the rules are actively wrong, not merely quiet), licences stated in free-text prose on the held-out split (so the deployed parser extracts nothing and escalates), and retrieval that returns two distractors alongside the match (so the passage must be chosen from the evidence before its licence can be read) -- would open headroom a model could cross and a rule could not. Nothing in the repository tested that claim until the GPU run.
**Decision:** Keep the reshaped task as the standard the planner fine-tune is measured against, and report B-3's answer entirely against it. The easy set stays in `artifacts/planner-dataset/easy-reference.jsonl` as evidence of what was rejected, not as a fallback: a future retrain is measured here or it is not comparable.
**Alternatives:** report against the original easy set (rejected by ADR-036 and now by the measurement too -- the rules score 100% on shapes `Diagnoser` names correctly, so the margin would be zero by construction); teach `Diagnoser` the five new shapes so the rules could compete (removes the headroom rather than crossing it, and a test asserts the baseline stays bad for exactly this reason); take targets from a larger model instead of the written teacher (makes the ceiling unreviewable, which is the opposite of what an interview-defensible result needs).
**Consequences:** The bet paid, and the size of the payment is on the record: on 300 held-out cases the QLoRA adapter scores **97.7% exact-match (293/300)** where the rules as deployed score **0.0%** and the rules handed licences they could not have parsed score **20.0%**, closing **97.1% of the 80-point gap** between the generous baseline and the teacher, while proposing a forbidden action on **1.0%** of cases against the baseline's **61.3%**. Each property of the reshape has a number attached: the out-of-set symptoms are the four the generous rules score 0/60 on and the model scores 60, 60, 57 and 56; the prose licences are why the deployed parser escalates on all 300; and the distractors did not defeat grounding, with **0 ungrounded actions** across 300 plans. `slow_drift` is the control the reshape deliberately left in -- the one symptom the rules get right -- and the model matches it at 60/60, which is the evidence that it learned the teacher's policy and not the complement of the baseline. Costs accepted and reported in `docs/EVALUATION.md` section 6: the teacher is a hand-written ceiling, so 97.7% is agreement with a written policy rather than with ground truth; both splits come from one generator, so this is distribution shift and not an independent corpus; three plans still propose a forbidden action and the safety gate rejected none of them, because symptom appropriateness is outside what the gate checks (ADR-027); and the adapter is not wired into `RemediationAgent`, which still plans with the rules.

## ADR-041 - Claude reads the chart, and the presence of its key is the only thing that selects it
**Status:** accepted (Phase 4, E-1)
**Context:** B-1 answered the serving question with a hosted OpenAI-compatible endpoint behind `VLM_ENDPOINT` / `VLM_API_KEY` / `VLM_MODEL`. That backend was built and contract-tested against a local fake, and then no key ever arrived (C-2), so its success path has only ever run against a fake and NFR-2 has never been measured. An Anthropic key is the credential that is actually obtainable here, which makes "explanations from a real model" reachable for the first time.
**Decision:** Add a second backend rather than swap the first. `ClaudeExplainer` calls Anthropic's Messages API with the rendered chart as a base64 `image` block and the episode's numbers as a `text` block beside it - the VLM4TS screen-then-verify shape, unchanged. Model `claude-sonnet-5` (the current Sonnet; `claude-sonnet-4-5` is not a current model ID), `effort: low` because reading one chart and writing four sentences is not a reasoning problem and this path has a latency budget, **no sampling parameters at all** because current Sonnet rejects `temperature` / `top_p` / `top_k` with a 400, `max_tokens` 400, and one retry rather than the SDK default of two. Selection is by key presence and nothing else: `ANTHROPIC_API_KEY` set means Claude, otherwise the endpoint backend, neither means unavailable exactly as before. The key is read from that environment variable only and passed to the client explicitly.
**Alternatives:** replace the endpoint backend (rejected: it is the interface B-1 was answered with, it is what eighteen contract tests exercise against a local fake, and it is the escape hatch for anyone serving their own VLM); point the existing OpenAI-compatible client at an Anthropic-compatible shim (rejected: the wire shapes differ where it matters - `image_url` against `source.data`, and a `temperature` that one provider requires and the other rejects outright - so the "compatibility" layer would be a place for silent breakage rather than a saving); let `anthropic.Anthropic()` resolve credentials through the SDK's own chain (rejected: it would also accept an OAuth profile or a token file, so whether the explainer runs would depend on machine state nothing in this repository documents, and "is it configured" would stop having one answer).
**Consequences:** The explainer can run against a real model, and the two backends share one `WindowExplainer` contract, so the never-raises promise, the counters and the absence semantics are written once rather than twice. Costs accepted: a second transport to keep working, a per-flagged-window API cost, and a third-party dependency on the rare path. And the limit that has to be said plainly - **no Anthropic key exists in this environment either.** Nothing here has been run against Anthropic. The success path is tested against an injected stub client, the local half of the cost is measured (render 54 ms p50, 28-32 KB of PNG), and the API half is not. NFR-2 remains unmeasured, exactly as it has been since B-1, and `docs/EVALUATION.md` section 7 says so rather than estimating it.

## ADR-042 - The explanation is evidence; it may not move the symptom or the query
**Status:** accepted (Phase 4, E-1)
**Context:** `docs/PROJECT_PLAN.md` says the VLM's explanation "feeds the agent's diagnoser as grounded evidence" and "becomes grounded input to the agent's diagnoser". Three readings of that are defensible and they differ entirely in how much authority a sentence written by a model gets: the explanation is recorded and read by a human; or it also widens the BM25 query, which decides which runbook passage is retrieved and therefore which actions are licensed; or it can refine the symptom itself.
**Decision:** The first. The explanation is carried in `Diagnosis.evidence` as `vlm_explanation`, reaches the trace and the operator, and touches nothing else. The symptom and the retrieval query stay derived from the detector's own numbers. An explanation that is absent, late, or wrong therefore changes the record a human reads and changes nothing the agent does.
**Alternatives:** let the explanation widen the retrieval query (this is the reading the architecture's own line invites - "retrieval widens what is considered; it never widens what is permitted" - and the licences and the gate would still bind; rejected here because a wrong explanation would retrieve a wrong passage, and a wrong passage licenses a different action set, so the failure is quiet and the committed CI quality baseline would have to move to accommodate it); let the explanation refine the symptom (rejected outright: `docs/EVALUATION.md` section 6.3 had just finished documenting that the gate checks blast radius and action class and *not* appropriateness to the symptom, so free text steering the symptom would aim at the one hole the gate does not cover).
**Consequences:** The plan's sentence is satisfied in the weakest way that is still true, and that is the point: the explanation is genuinely present in the diagnosis and genuinely inert. The agent-quality baseline in CI is untouched, because nothing about retrieval or planning changed. A test asserts the inertness directly - a deliberately misleading explanation claiming a safety interlock failure produces byte-identical symptom, query and summary. Cost accepted: this is the least useful of the three readings. The explanation informs the human and does not yet make the agent better at its job, and if it should, that is a new decision with a new measurement behind it rather than a default nobody chose.

## ADR-043 - The Iceberg catalog is a JDBC catalog in the application Postgres, not a REST service
**Status:** accepted (Phase 3)
**Context:** Iceberg needs a catalog: the thing that maps a table name to its current metadata pointer and makes a commit atomic. The canonical local setup is an Iceberg REST catalog container alongside MinIO. The only ready-made REST image is `apache/iceberg-rest-fixture`, which upstream labels a **test fixture**; Lakekeeper and Apache Polaris are real REST catalog servers but each is a substantial service to stand up and operate. Meanwhile this stack runs on a Docker VM with 8.1 GB, already holding Kafka, Postgres, ClickHouse and MinIO.
**Decision:** Use pyiceberg's `SqlCatalog` over the Postgres instance that already holds episodes and app state, with the data files on MinIO. A JDBC catalog is one of Iceberg's own catalog implementations, not a stand-in for one. The catalog tables live in the application database, which is defensible on its own terms: a catalog *is* application state, it is exactly what ADR-006 says that database is for, and it is backed up and restored with everything else.
**Alternatives:** the REST fixture image (rejected: shipping a container upstream calls a test fixture and then describing the result as production-shaped is the kind of claim this repository's honesty rules exist to stop); Lakekeeper or Polaris (rejected for now on cost, not on merit -- either is a real answer and either is a bigger lift than the rest of this phase combined; the client code is catalog-agnostic, so swapping is a settings change); SQLite catalog on a local filesystem warehouse (rejected: it drops object storage entirely, so the S3 path that makes this a lake rather than a directory would never be exercised, and `docs/PROJECT_PLAN.md` section 6 says "Iceberg on object storage").
**Consequences:** No extra container, and one fewer service to be down. Measured with the full default stack up: ClickHouse 203 MB, Kafka 910 MB, MinIO 67 MB, Postgres 42 MB -- 1.2 GB of 8.13 GB, which is what lets these start by default rather than behind a profile. Costs accepted, and they are real: **the lake's catalog now depends on the application database being up**, so Postgres is load-bearing for two of the three stores rather than one; a catalog outage and an app-state outage are the same outage. And the multi-engine story is weaker than a REST catalog's -- another engine reaching this lake needs JDBC access to that Postgres and the credentials for it, rather than an HTTP endpoint. Neither cost binds at this scale, and both are the reason to revisit this if the lake ever has a second reader.

## ADR-044 - The lake sink's offsets live in the Iceberg snapshot, not in Kafka
**Status:** accepted (Phase 3)
**Context:** A sink that consumes Kafka and writes to a lake has to record how far it got. The ordinary answer is a consumer-group offset commit, which leaves two stores holding one fact: the offsets say a batch was handled, the table says which rows exist, and a crash between the two makes them disagree. Disagreement in one direction is a duplicate and in the other is a gap. Iceberg commits are atomic and every snapshot carries a free-form summary, so the position can be stored *inside* the same commit as the data it describes.
**Decision:** Each append writes the consumed Kafka offsets into the snapshot summary under `vigil.offsets`, and the sink resumes by seeking to what the current snapshot says. Kafka's own offset store is switched off (`enable.auto.commit: False`, explicit `assign` rather than `subscribe`), so there is exactly one record of position and it is the one that was committed with the rows. The delivery claim is therefore **effectively-once into the lake**: a crash re-reads the batch that was in flight, which was never committed, so re-writing it creates no duplicate.
**Alternatives:** commit Kafka offsets after the append (rejected: this is the two-store problem, and the window is small rather than absent -- small windows are what produce the duplicates nobody can reproduce); at-least-once plus dedupe on read (rejected: the table alone would never be trustworthy, every reader would have to remember to dedupe, and a reconciliation harness auditing a deduplicated view audits the dedupe rather than the pipeline); a separate offsets table in Postgres (rejected: two stores again, with the added twist that they would be two different databases).
**Consequences:** The lake holds no duplicates and no gaps, and the claim rests on Iceberg's commit atomicity rather than on our bookkeeping being lucky. Verified by running it: 8,000 readings landed, the sink was restarted with `--from-beginning`, and it read **0 records** because the snapshot's offsets won over the flag; 3,600 further readings then resumed exactly at the boundary, 0 duplicate rows across 2 snapshots. `python lake.py --verify` re-checks the claim against the stored bytes and exits non-zero if it fails. Costs accepted: the sink cannot share a consumer group with anything (it manages its own assignment), so it does not scale by adding members -- partition-level parallelism would need the offsets map split per worker, which is a real change and not a tuning knob. Batch size now decides commit frequency and therefore snapshot count, and Iceberg dislikes very frequent small commits, so the 10,000-reading default is a floor that matters rather than an arbitrary number.

## ADR-045 - ClickHouse serves readings and window scores; episodes are not mirrored into it
**Status:** accepted (Phase 3)
**Context:** ADR-006 splits storage three ways, and the serving third had never been built: raw readings and per-window detector scores existed only on Kafka, which is to say they were not queryable at all once retention passed. The open question when adding ClickHouse was whether episodes should also be mirrored there so the dashboard could serve everything from one store.
**Decision:** ClickHouse holds readings and window scores only. Episodes stay in Postgres and are not copied. `/episodes` and `/detectors` keep reading Postgres; `/metrics`, `/metrics/{channel}` and `/scores` are new and read ClickHouse; `/health` reports both stores separately, because ClickHouse being down costs serving panels and costs episodes nothing.
**Alternatives:** mirror episodes into ClickHouse (rejected: it buys no query speed -- a run produces 147 episodes, which is not an OLAP problem -- and it costs a consistency question nobody asked for, two copies that can disagree plus a freshness panel that would have to exist to make the mirror honest); move episodes to ClickHouse outright (rejected: they need a transactional upsert on `(channel, t_start_ms, raised_by)` and a foreign key to the context event that explains them, which is what Postgres is for and what ClickHouse deliberately is not).
**Consequences:** One writer per table and no mirrors, so no endpoint has to decide which copy to believe. The rollup query the store exists for -- a per-channel summary over every reading ever ingested -- is answered from a per-minute aggregate rather than by scanning the raw table. Costs accepted: the dashboard now reads from two stores, so a panel can be stale in one and fresh in the other and the UI has to be honest about which; and a query joining episodes to the raw readings underneath them has no single place to run, which is the price of the split and would be paid by a mirror in a different currency.

## ADR-046 - A reading is identified by (channel, seq, event_ts), because the producer's sequence restarts
**Status:** accepted (Phase 3, corrects an assumption in `docs/CORRECTNESS.md` section 2)
**Context:** The platform identifies a reading by `(channel, seq)`, a per-channel sequence assigned at the ingestion boundary and dense by construction. Both new stores were built on that: ClickHouse's `ReplacingMergeTree` keyed on it, the lake's duplicate check grouped by it. Running the stack twice showed the premise is narrower than it reads. The generator restarts its sequence at 1 every run, so the lake held two genuinely different readings -- eight minutes apart, different values -- both carrying `seq=5` on the same channel. **The sequence is dense within one producer lifetime, not across the table's history.** Keyed on `(channel, seq)`, ClickHouse would have deleted the older of the two at merge time and reported it as a successful dedupe, and the lake counted 3,600 distinct readings as duplicates.
**Decision:** Identity in both stores becomes `(channel, seq, event_ts)`. A genuine at-least-once redelivery carries an identical event timestamp, so it still collapses; two distinct readings that reuse a sequence number no longer collide. The lake's audit reports the two causes separately -- `duplicate_rows` for redelivery, which is a fault in the sink, and `reused_seq` for sequence reuse, which is a fact about the producer.
**Alternatives:** add a producer epoch to the wire format so identity is `(channel, epoch, seq)` (the textbook fix, and it would make the dense-sequence invariant well-defined per epoch; rejected for now on blast radius -- it changes a format shared by the wire codec, the generator, the MQTT bridge, the ledger, the Flink job and the reconciliation harness, turning a Phase 3 task into a Phase 1 refactor, and every stored reading predates it); document that producers must not restart against a live lake (rejected: it leaves ClickHouse silently deleting real readings, which is data loss reported as success, and a real fleet device rebooting would do exactly what the generator did).
**Consequences:** Both stores now distinguish redelivery from sequence reuse, and a test in each pins the distinction. The remaining hole is narrow and worth naming: two distinct readings sharing a channel, a sequence number *and* an event timestamp to the millisecond would still collapse -- and nothing downstream could tell them apart anyway, so there is no version of this that separates them. The live reconciliation ledger is unchanged and still reports a producer restart as `reordered`, which is correct: from the stream's point of view the sequence did regress. What changed is that the *stored* audits no longer read that as loss or duplication. `docs/CORRECTNESS.md` section 2's identity claim is now scoped to a producer lifetime rather than stated unconditionally.
